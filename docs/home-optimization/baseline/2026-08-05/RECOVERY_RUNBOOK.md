## 1. 복구 대상 구분

- [ ] 메인 HTML 문제인지 확인한다. — 증상 예: 빈 화면, 스크롤 불가, JavaScript 구문 오류.
- [ ] Cloud Function 문제인지 확인한다. — 증상 예: 모든 데이터 API 5xx, 생성·참여 저장 실패.
- [ ] GCS manifest 문제인지 확인한다. — 증상 예: manifest 404, 참조 JSON 누락, 새·이전 상품군 혼합.
- [ ] 특정 기능 플래그 문제인지 확인한다. — 증상 예: MD PICK만 실패하고 나머지 메인은 정상.
- [ ] 개인정보·중복 저장 문제면 성능과 관계없이 즉시 신규 기능을 중지한다.

## 2. 복구 전 1분 확인

- [ ] 장애 시작 시각을 기록한다.
- [ ] 영향 URL과 로그인 여부를 기록한다.
- [ ] PC와 MO 중 어느 쪽에서 발생하는지 기록한다.
- [ ] 브라우저 콘솔 첫 오류와 실패한 네트워크 URL을 기록한다.
- [ ] 현재 root manifest와 revision을 기록한다.
- [ ] 현재 게시판 HTML 원문을 별도로 보존한다.
- [ ] 현재 Git 작업트리의 미커밋 변경을 제거하지 않는다.

## 3. 기능 플래그 복구

- [ ] 문제가 난 기능 플래그 하나만 먼저 OFF로 바꾼다.
- [ ] 새 manifest를 브라우저가 읽었는지 revision으로 확인한다.
- [ ] 1분 안에 정상화되지 않으면 V2 전체 플래그를 OFF로 바꾼다.
- [ ] 신규 renderer가 중단되고 legacy renderer 하나만 동작하는지 확인한다.

## 4. 메인 HTML 복구

- [ ] 현재 게시판 HTML을 먼저 내보내거나 복사해 보존한다.
- [ ] 기준선에서 지정한 직전 정상 HTML을 게시판 소스보기에 등록한다.
- [ ] PC 비로그인에서 메인 섹션과 스크롤을 확인한다.
- [ ] MO 비로그인에서 가로 스크롤과 하단 메뉴를 확인한다.
- [ ] 로그인 후 나의 모임과 내예약을 확인한다.
- [ ] 상품카드에서 상세를 열고 닫을 수 있는지 확인한다.

## 5. GCS 데이터 복구

- [ ] root manifest가 참조하는 모든 객체가 200인지 확인한다.
- [ ] 상품군 문제라면 `previousPublicationRevision`의 catalog가 존재하는지 확인한다.
- [ ] 이전 catalog 객체를 검증한 뒤 root manifest만 이전 revision으로 전환한다.
- [ ] 현재 홈 manifest v1에는 이전 홈 카드 revision이 기록되지 않는 점을 확인한다.
- [ ] 홈 카드 복구 전에 직전 정상 홈 카드 URL을 배포 기록에서 찾는다.
- [ ] root manifest를 바꾸기 전에 가격·날짜·대표상품 핵심 필드를 비교한다.
- [ ] 브라우저에서 manifest revision과 실제 JSON revision이 일치하는지 확인한다.
