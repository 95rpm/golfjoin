# PC 로그인 콜드 HAR 3회 통합 기준선

## 1. 측정 완료 범위

- [x] 같은 로그인 계정과 PC 환경에서 측정했다.
- [x] Chrome Network의 `Disable cache`를 사용했다.
- [x] 새로고침 뒤 측정 중 스크롤·클릭하지 않았다.
- [x] run01·run02·run03 원본 HAR을 저장했다.
- [x] 세 원본을 개인정보 제거 후 분석했다.
- [x] 세 회차 중앙값과 편차를 계산했다.
- [ ] Web Vitals와 Performance trace는 별도 측정이 필요하다.

이 보고서의 `범위 편차`는 `(최댓값 - 최솟값) ÷ 중앙값`이다. 숫자가 작을수록 세 번의 결과가 비슷하다는 뜻이다.

## 3. 확정된 병목

### 3.1 MD PICK은 다운로드가 아니라 요청 시작이 늦다

지연 프리로드 이미지의 실제 다운로드는 각 회차에서 약 18~42ms였다. 그러나 요청은 14.62초, 16.71초, 17.00초에 시작됐다.

- [x] 이미지 서버 속도가 주원인이 아니다.
- [x] `scheduleMdPickImagePreload()`의 8초 타이머와 timeout 없는 `requestIdleCallback(run)`이 직접 지연 경로다.
- [x] 2단계에서 고정 8초 프리로드와 중첩 idle 대기를 제거하는 우선순위가 확정됐다.

### 3.2 로그인 보조 데이터가 늦고 순차 실행된다

코드는 홈 초기화 후 1.5초 타이머와 `requestIdleCallback(..., { timeout: 2500 })`을 거쳐 보조 hydration을 시작한다. 회원 데이터 내부에서는 Builder 신청, 참여 신청, 찜, 통계를 차례로 `await`한다.

- [x] Bootstrap이 207~272ms로 빠른 회차에서도 보조 요청은 8.76~9.66초에 시작했다.
- [x] 공개·회원 new schedule 두 요청 다음에 `join → wishes → stats` 폭포가 재현됐다.
- [x] 서버 응답 최적화만으로는 초기 로그인 화면 지연을 해결할 수 없다.

### 3.3 늦은 취향맞춤 배경이 Finish 편차를 만든다

세 회차의 마지막 요청은 모두 `taste_bg3.webp`였다. 요청 시작은 16.63초, 33.73초, 19.00초였고 다운로드는 수십 ms 이내였다.

- [x] 마지막 요청 종료의 89.9% 편차는 주로 늦은 배경 이미지 요청 시점에서 발생했다.
- [x] `Finish`만으로 사용자가 볼 수 있는 화면의 완료 시간을 판단하면 안 된다.
- [ ] Performance trace에서 취향맞춤 DOM 생성과 배경 적용 시점을 연결해 확인한다.

- [ ] 2단계에서 표시 크기에 맞는 경량 변형본과 URL 단위 중복 방지를 검토한다.

### 3.5 반복 실패와 병목 제외 항목

- [x] 원 홈페이지 `getEventTab`·`getEventGoodsList`는 매회 합계 633 bytes이고 15~50ms 수준이어서 병목이 아니다.

## 4. 이 기준선으로 확정할 값

| 용도 | 사용할 값 | 이유 |
|---|---:|---|
| 초기 HTML 처리 기준 | DOMContentLoaded 중앙값 1,986ms | 세 회차 편차 10.9% |
| 초기 네트워크 무게 | 전체 전송량 중앙값 5,524,351 bytes | 세 회차 편차 4.2% |
| 이미지 무게 | 이미지 전송량 중앙값 3,486,938 bytes | 세 회차 편차 6.7% |
| 로그인 데이터 완료 기준 | 마지막 회원 API 종료 중앙값 11,650ms | 세 회차 편차 1.5% |
| MD PICK 개선 기준 | 지연 프리로드 시작 중앙값 16,705ms | 원인이 명확하고 편차 14.3% |

`Load`와 전체 `Finish`는 지연 이미지 생성 시점의 영향을 크게 받아 이번 최적화의 단독 합격 지표로 사용하지 않는다. 1단계 관측 장치에서 LCP, CLS, long task, 실제 이미지 표시 시점을 추가한 뒤 사용자 체감 지표를 확정한다.
