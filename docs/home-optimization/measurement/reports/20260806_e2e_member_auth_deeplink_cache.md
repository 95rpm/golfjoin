# 회원 로그인·딥링크·캐시 E2E 결과

## 결론

- PC 6개와 모바일 6개, 총 12개 시나리오가 모두 통과했다.
- 실제 회원 계정, 로그인 쿠키, 비밀번호, 인증번호는 사용하거나 저장하지 않았다.
- 모든 회원 정보는 `E2E_*` 합성값이며 구글시트 읽기 응답도 브라우저 안에서 합성했다.
- 알 수 없는 POST와 운영 쓰기 요청은 테스트 라우터에서 차단했다. 실행 중 차단된 쓰기 시도는 0건이었다.

쉽게 말하면, 실제 고객 데이터에 손대지 않고도 “로그인한 사람이 바뀌었을 때 데이터가 섞이는지”와 “알림톡 링크가 중복으로 열리는지”를 자동 검사할 수 있게 됐다.

| 세션 로그인 우선 | 같은 문서에 검증 세션이 있으면 오래된 CookieData보다 세션 회원을 사용하는지 | 통과 | 통과 |
| 프로필 미완성 | 성별·출생연도·직업·핸디·스타일이 빠진 회원에게 추가정보 입력 화면을 여는지 | 통과 | 통과 |
| A 로그아웃 후 B 로그인 | A의 찜·참여·생성 일정 캐시를 지우고 B의 회원 키로 전환하는지 | 통과 | 통과 |
| 로그인 복귀 딥링크 | 일정 응답을 2.5초 늦춰도 나의 모임 상세를 정확히 한 번 여는지 | 통과 | 통과 |
| 내예약 재진입 비교 | 첫 진입과 닫은 뒤 재진입의 회원 API 목록, 캐시 회원 키, 쓰기 요청을 비교하는지 | 통과 | 통과 |

## 딥링크 경합 결과

로그인 복귀 URL의 `afterLogin=my-section`과 일정 ID를 먼저 전달하고, 해당 일정이 들어 있는 `home_bootstrap_light` 응답을 2.5초 지연했다.

1. 첫 시도에서 아직 일정을 찾지 못했다.
2. 코드가 대상 일정과 탭 파라미터를 다시 복원했다.
3. 회원 일정 데이터가 도착한 뒤 나의 모임 위치로 이동했다.
4. 상세 모달의 `openDetail` 호출은 PC와 모바일 모두 정확히 1회였다.
5. 모달이 열린 뒤 3초를 더 기다려도 재실행되지 않았다.
6. 처리된 `afterLogin`, `golfjoinOpen`, `scheduleId`는 주소에서 제거됐다.

## 내예약 재진입 API 기준선

첫 진입과 두 번째 진입 모두 현재 다음 3개 읽기 요청을 실행한다.

| 순서 | 데이터 | 회원 범위 |
|---:|---|---|
| 1 | `new_schedule_applications` 공개 생성 일정 | 공개 |
| 2 | `new_schedule_applications` 내 생성 일정 | 현재 회원 |
| 3 | `join_applications` 내 참여 일정 | 현재 회원 |

- `builderApplicationsSheetReadCache`와 `joinApplicationsSheetReadCache`는 모두 현재 회원의 `memberKey`로 저장됐다.
- A회원 캐시를 B회원이 읽는 현상은 없었다.
- 다만 캐시가 60초 이내로 새로워도 내예약을 닫았다가 다시 열면 위 3건을 다시 요청한다.
- 따라서 현재 동작은 정합성 면에서는 안전하지만, 재진입 속도와 요청 수는 8단계 회원 데이터 최적화에서 줄일 수 있다.
