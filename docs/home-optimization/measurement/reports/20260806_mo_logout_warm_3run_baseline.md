## 4. 확정된 결론

### 4.1 HTTP 캐시는 정상 작동한다

- [x] 세 실행의 전송량 편차는 0.017%다.
- [x] CSS 9개·JavaScript 40개·폰트 2개는 세 번 모두 0 bytes다.
- [x] 상품이미지 14개는 세 번 모두 0 bytes다.
- [x] 홈 카드 JSON은 세 번 모두 0 bytes다.

따라서 Warm에서 대표이미지가 늦는 문제를 이미지 저장소나 다운로드 속도로 설명할 수 없다.

### 4.2 8초 타이머는 Cold와 Warm에서 동일하다

- Cold 중앙값: 8,009ms
- Warm 중앙값: 8,005ms
- 차이: 4ms

핵심 상품이미지 묶음 뒤 마지막 `goodSeq=30001242`가 등록되는 시점은 캐시 상태와 관계없이 약 8초다. Phase 2의 최우선 제거 대상이다.

### 4.3 초기 일부 이미지 등록 순서가 불안정하다

run01·run03은 첫 4개가 약 4.7~5.2초에 먼저 등록됐지만 run02는 13개가 약 9.5초에 한 번에 등록됐다. 같은 데이터라도 렌더·idle callback 순서에 따라 사용자가 먼저 보는 이미지 시점이 달라질 수 있다. Phase 1 계측에서 호출 경로를 구분하고 Phase 2에서 화면 상단 이미지를 명시적 우선순위로 고정한다.

### 4.4 Warm에서는 HTML이 전송량 대부분이다

메인 HTML은 약 490,462 bytes로 전체 Warm 전송량의 약 93.8%다. Phase 13의 CSS·JavaScript 외부화와 HTML 경량화 효과를 비교할 모바일 기준값이다.

### 4.5 버전 catalog 재검증이 남는다

상품군 catalog는 버전 경로인데도 세 번 모두 304 / 13 bytes 재검증한다. 전송량은 작지만 불필요한 왕복 후보이므로 revision 불변성이 보장된 뒤 장기 캐시로 전환한다.
