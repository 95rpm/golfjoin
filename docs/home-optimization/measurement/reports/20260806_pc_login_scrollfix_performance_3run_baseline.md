## 3. 확정된 원인

초기 진입은 다음 흐름을 반복한다.

1. 부트스트랩 응답 직후 약 2.85~3.48초의 긴 microtask가 실행된다.
2. `scheduleHomeRender()`가 `renderJoins()` 전체 홈 렌더를 예약한다.
3. 전체 렌더 한 번이 최대 3.77초 동안 메인 스레드를 점유한다.
4. 이어서 `scheduleMdPickSectionRender()`가 MD PICK을 별도로 다시 렌더한다.
5. 회원 일정·참여·찜·통계 데이터가 차례로 도착할 때 같은 경로가 다시 예약된다.

`requestIdleCallback`은 실행 시작 시점을 늦출 뿐 작업을 여러 프레임으로 나누지 않는다. 따라서 콜백이 시작된 뒤에는 스크롤·클릭·후속 Promise 처리가 수백 ms~수 초 기다릴 수 있다.

## 4. HAR 가설 수정

HAR에서는 공개 일정 응답 뒤 `join_applications` 시작까지 2.17~2.62초 구간이 반복돼 응답 후 Builder 행 병합·캐시 동기화 비용을 의심했다. Performance trace의 실제 완료 간격은 46.9~55.7ms였다.

- [x] 서버 응답 후 행 병합만 2초 이상 실행된다는 가설은 기각한다.
- [x] 일정 네트워크와 겹치거나 앞뒤로 실행되는 반복 전체 렌더가 후속 처리와 사용자 입력을 지연시키는 구조를 1순위 원인으로 확정한다.
- [x] 서버 API 속도는 렌더 예약이 서로 합쳐지는 정도를 바꾸지만, 병목 함수 자체는 세 번 모두 같다.

## 5. 편차 판정

병목의 종류와 소스 위치는 3회 모두 같지만 long task 합계와 렌더 총시간의 상대 범위가 20%를 넘는다. 이는 측정 실패로 숨기지 않고 현재 시스템이 데이터 응답 순서에 민감하다는 성능 결함으로 기록한다.

- [x] 원인 재현성: 통과 — 동일 렌더 경로가 3회 모두 장시간 실행됐다.
- [ ] 수치 재현성: 미통과 — 주요 렌더 시간 상대 범위가 29.4~84.6%다.
- [x] 일정 API 완료 후 다음 API 간격: 통과 — 상대 범위 16.8%다.
- [x] 개선 전 중앙값은 비교 기준으로 보존한다.
- [ ] Phase 0 전체 완료 조건은 아직 충족하지 않았다.

## 6. 안전한 다음 작업

기능 데이터는 건드리지 않고 Phase 1 관측 장치를 먼저 추가한다.

- [ ] `scheduleHomeRender()` 호출 원인과 데이터 revision을 기록한다.
- [ ] 실제 `renderJoins()` 시작·종료·HTML 생성·DOM 반영 시간을 분리한다.
- [ ] `scheduleMdPickSectionRender()` 호출 원인과 DOM 변경 여부를 기록한다.
- [ ] 부트스트랩 직후 3초대 microtask의 내부 단계를 `Performance.mark`로 나눈다.
- [ ] 회원 일정·참여자·현재인원 데이터가 최신 상태일 때만 렌더 완료로 판정한다.

참여자 아이콘, 모임장·나 배지, 현재인원, 성별 구성은 회원 데이터 도착 때 반드시 갱신돼야 한다. 따라서 단순히 두 번째 렌더를 삭제하지 않고, 여러 상태 변경을 하나로 합친 뒤 최신 데이터로 한 번 렌더하는 구조를 목표로 한다.
