## 2. 초보자를 위한 결론

run02에서도 같은 화면 렌더 함수가 메인 스레드를 수 초 동안 막았다. 실행 횟수는 run01보다 줄었지만, 전체 홈 렌더 한 번이 최대 3.77초 걸렸다. 실행 횟수가 적어진 것만으로 안전해진 것이 아니라 데이터 도착 순서에 따라 렌더 요청이 합쳐지는 정도가 달라진 것으로 해석해야 한다.

따라서 두 번의 측정에서 공통으로 확인된 문제는 다음과 같다.

- 같은 초기 진입 안에서 전체 홈 렌더와 MD PICK 렌더가 반복된다.
- `requestIdleCallback`으로 늦춰도 실행을 시작한 뒤에는 한 작업이 수백 ms~수 초 동안 계속된다.
- 이 시간에는 스크롤·클릭·다음 JavaScript 처리가 기다릴 수 있다.

## 5. 호출 횟수가 달라진 이유에 대한 판단

운영 trace의 함수 위치는 run01과 동일했다.

| 운영 trace 위치 | 기능 | run01 | run02 |
|---|---|---:|---:|
| `plan_view` 61,225줄 | `scheduleHomeRender()` → `renderJoins()` | 3회 | 2회 |
| `plan_view` 61,266줄 | `scheduleMdPickSectionRender()` → `renderMdPickSectionOnly()` | 3회 | 2회 |

run02에서는 일정 API가 run01보다 빨리 끝났고 여러 데이터 변경이 렌더 예약 하나로 합쳐질 기회가 더 많았다. 이 때문에 호출 수가 줄었을 가능성이 높다. 이는 trace에 근거한 추론이며 run03에서 다시 확인한다.

중요한 점은 호출 수가 변해도 병목이 사라지지 않았다는 것이다. 전체 홈 렌더 한 번의 최대 실행 시간이 run01 3.16초에서 run02 3.77초로 오히려 늘었다.
