## 초보자를 위한 설명

`preconnect`는 실제 데이터를 요청하기 전에 서버와 악수해 두는 기능이다. 악수가 미리 끝나면 빨라질 수 있지만, 이미 다른 요청이 연결을 열고 있거나 화면에 필요한 이미지가 즉시 요청되면 별도 악수가 중복돼 오히려 자원을 쓸 수 있다. 그래서 같은 화면을 기존 방식과 가상 후보로 반복 측정해 실제 이득이 확인될 때만 적용한다.

## 측정 방법

- [x] PC와 MO 운영 응답에 기존 `preconnect`·`dns-prefetch`가 없는지 확인했다.
- [x] 현재 로컬 HTML을 운영 외곽 페이지에 결합한 기존 조건을 만들었다.
- [x] 같은 HTML의 `<title>` 바로 뒤에 두 도메인의 `preconnect crossorigin`만 가상으로 넣은 후보를 만들었다.
- [x] 브라우저 캐시를 끄고 Chrome DevTools Protocol의 첫 응답 연결 시간을 기록했다.
- [x] PC 기존 3회·후보 3회, MO 기존 3회·후보 3회, 총 12회를 실행했다.
- [x] 운영 쓰기 API와 실제 회원정보는 사용하지 않았다.

측정 자동화: `tests/e2e/diagnostics/preconnect-measurement.spec.js`

## 결과

### GCS 첫 이미지 연결

첫 대상은 모든 회차에서 `hero_banner.webp`, 프로토콜은 HTTP/2였다.

| 환경 | 조건 | DNS 3회(ms) | DNS 중앙값 | TCP·TLS 포함 연결 3회(ms) | 연결 중앙값 | 완료된 연결 재사용 |
|---|---|---|---:|---|---:|---:|
| PC | 기존 | 2.834 / 1.472 / 2.720 | 2.720 | 79.281 / 79.944 / 38.857 | 79.281 | 0/3 |
| PC | 후보 | 7.023 / 2.679 / 2.416 | 2.679 | 80.080 / 85.029 / 38.973 | 80.080 | 0/3 |
| MO | 기존 | 1.891 / 2.577 / 3.357 | 2.577 | 77.175 / 82.381 / 38.664 | 77.175 | 0/3 |
| MO | 후보 | 2.211 / 2.265 / 1.905 | 2.211 | 38.062 / 76.310 / 37.707 | 38.062 | 0/3 |

MO 후보 중앙값만 보면 작아졌지만 후보도 완료된 연결을 한 번도 재사용하지 못했다. 기존과 후보 모두 약 38ms와 76~85ms 두 구간으로 흔들렸고 PC 후보는 오히려 1.0% 느렸다. 힌트 직후 히어로 이미지가 바로 요청돼 사전 연결이 끝날 여유가 없으므로 MO 숫자를 `preconnect` 효과로 판정할 수 없다.

### Cloud Function 첫 공개 API 연결

첫 대상은 모든 회차에서 `home_bootstrap_light`였다.

| 환경 | 기존 연결 재사용 | 후보 연결 재사용 | 추가 절감 |
|---|---:|---:|---:|
| PC | 3/3 | 3/3 | 없음 |
| MO | 3/3 | 3/3 | 없음 |

Cloud Function은 별도 힌트가 없는 기존 조건에서도 첫 응답이 이미 완료된 연결을 재사용했다. 후보가 줄일 DNS·TCP·TLS 시간이 남아 있지 않았다.
