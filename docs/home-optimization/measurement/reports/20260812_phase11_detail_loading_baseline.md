# 11단계 상품상세·여행기간·항공편 운영 기준선

## 결론

`CA9CFB31...` 운영본의 상품상세 껍데기는 현재 표본에서 PC p75 92.4ms, MO p75 63.7ms로 100ms 목표를 통과했다. 그러나 상품군 가용일 네트워크 응답을 받은 뒤에만 모달을 여는 구조라서 네트워크가 느린 상황에도 100ms를 보장하는 상태는 아니다.

더 큰 낭비는 모달을 연 다음 발생한다. 3개 기간으로 구성된 상품군 하나를 열 때 선택 상품 상세 1건뿐 아니라 기간 문구를 만들기 위한 나머지 상품 상세 2건까지 `goods_view` 총 3건을 요청했다. 동시에 일반 상세에 필요하지 않은 전체 상품 파일 `golfjoin_home_summary.json`도 매번 시작됐다.

## 항공편 관찰

운영 항공팩 표본 `goodSeq=30001242`, `eventSeq=30269532`는 `goods_view` 안에 완성된 항공 일정이 포함되어 별도 `flight_schedule` 요청을 만들지 않았다. 상세 완료는 PC 약 236~257ms, MO 약 207~229ms였고 모달 닫기는 PC p75 75ms, MO p75 76ms였다.

따라서 이 표본은 현재 정상 빠른 경로를 증명하지만, `flight_schedule`이 필요한 상품의 느린 응답까지 대표하지 않는다. 구현 검증에서는 항공 응답을 강제로 지연·실패시키는 자동시험으로 모달 닫기, 내부 스크롤, 기간 전환이 독립적인지 확인해야 한다.

## 코드상 원인

1. `openMdPickProductDetail()`이 상품군 가용일 전체를 `await`한 뒤 `showMdPickDetailProduct()`를 호출한다.
2. `renderDetailContent()`가 열릴 때 `hydrateDetailProductFamilyPeriodMetadata()`가 자동 실행되고 다른 기간의 `goods_view`를 최대 2개씩 병렬로 읽는다.
3. `getBuilderProductSource()`는 단순 조회처럼 보이지만 내부에서 `ensureExternalGolfJoinProductsLoaded()`를 실행한다.
4. 상세 캐시 키는 `goodSeq:eventSeq`뿐이며 발행본 `detailRevision`이 없다.
5. 기간 전환과 모달 닫기에 상세·항공 요청 세대와 취소 소유권이 없다.
6. 항공편 실패 상태에는 안내문만 있고 사용자가 다시 시도할 버튼이 없다.

## 안전한 구현 결정

- 카드 정보로 모달 껍데기를 먼저 열되, 실제 신청 대상 행사는 가용일 검증 결과가 나온 뒤 확정한다. 임시 대표 행사를 곧바로 신청 대상으로 사용하지 않는다.
- 상품군 catalog에 골프 일수·홀수·출발 패턴이 준비되기 전에는 다른 기간의 상세를 미리 읽지 않고 `확인 중` 같은 안전한 문구를 유지한다.
- `getBuilderProductSource()`를 순수 캐시 조회로 바꾸고 전체 상품 로딩은 Builder·캘린더가 명시적으로 요청할 때만 실행한다.
- 선택한 상품의 공개 상세 스냅샷만 읽고, 스냅샷이 없거나 계약 검증에 실패하면 현재 `goods_view` 파싱으로 자동 복구한다.
- 회원가, 회원별 혜택, 실시간 좌석, 동적 항공편은 공개 스냅샷에 저장하지 않는다.
- 기간 선택마다 세대를 증가시켜 늦게 도착한 이전 응답을 버리고, 모달을 닫으면 해당 모달이 소유한 불필요한 요청을 중단한다.
- 항공편은 독립 영역에서만 로딩 상태를 보이고, 5초 초과·실패 시 다시 시도 버튼을 제공한다.
