# 8단계 로그인·개인 데이터 최적화 후보 보고서

## 1. 결론

- [x] 같은 회원의 생성 일정·참여 일정·찜 조회를 데이터형별 Promise 하나로 합쳤다.
- [x] 서로 독립적인 회원 조회를 병렬로 실행한다.
- [x] 공개 bootstrap에 이미 포함된 생성 일정 공개 목록을 다시 요청하지 않는다.
- [x] 공개 요약 행은 전체 신청 행으로 재정규화하지 않고 전용 요약 병합기로 처리한다.
- [x] 회원 전용 생성 일정 캐시에는 회원 전체행만 저장해 공개 요약과 개인 상세의 역할을 분리한다.
- [x] 내예약은 60초 이내 같은 회원 캐시를 즉시 표시하고 불필요한 재조회를 생략한다.
- [x] 캐시를 세션 세대·회원키·데이터형으로 구분한다.
- [x] 로그아웃·회원 전환·늦게 도착한 이전 회원 응답을 차단한다.
- [x] 개인 응답을 브라우저와 중간 공유 캐시에 저장하지 않도록 서버 헤더를 추가했다.
- [x] PC·모바일 후보 회귀검사를 모두 통과했다.
- [x] Cloud Function을 운영 배포하고 개인 경로 2종의 캐시 금지 헤더와 공개 경로의 비적용을 확인했다.
- [ ] 후보 HTML 운영 배포 후 실제 회원 요청 수와 화면 결과를 확인해야 한다.
- [ ] Secret Tour 인증 세션과 요청 회원의 일치 여부를 서버에서 검증하려면 same-origin BFF 또는 짧은 서명 토큰 연동이 필요하다.

## 2. 초보자용 설명

기존 로그인 화면은 같은 회원의 같은 데이터를 거의 동시에 여러 함수가 요청할 수 있었다. 또한 공개 메인 응답에 이미 들어 있는 모임 목록을 다시 요청하고, 내예약을 다시 열 때 방금 받은 회원 데이터를 곧바로 재조회할 수 있었다.

이번 후보는 진행 중인 요청을 회원별 대기표에 등록한다. 같은 회원이 같은 종류의 데이터를 다시 요청하면 새 네트워크 요청을 만들지 않고 진행 중인 Promise를 함께 기다린다. 생성 일정·참여 일정·찜은 서로 독립적이므로 차례로 기다리지 않고 동시에 받는다.

캐시에는 단순히 회원 번호만 저장하지 않는다. 로그인 세대, 회원키, 데이터 종류를 함께 기록한다. 로그아웃하거나 A회원에서 B회원으로 바뀌면 세대를 올리고 이전 캐시를 비운다. A회원 요청이 늦게 끝나도 현재 세대와 회원키가 다르면 화면에 반영하지 않는다.

| 항목 | 기존 기준선 | 후보 | 결과 |

## 6. 보안 경계

이번 변경은 개인 응답의 캐시 혼입과 브라우저 내부 회원 전환 문제를 줄이지만 서버 인증을 새로 만들지는 않는다. 현재 Cloud Function은 Secret Tour 로그인 세션을 직접 검증할 신뢰 가능한 쿠키나 서명 토큰을 받지 못하고, 클라이언트가 보낸 회원 식별자로 조회한다.

- [x] 인증 구조 없이 통합 개인 API를 새로 만들지 않았다.
- [x] 개인 응답의 브라우저·공유 캐시 저장을 금지했다.
- [x] A→B 브라우저 캐시 혼입을 자동검사했다.
- [ ] Secret Tour same-origin BFF 또는 짧은 서명 토큰을 만든다.
- [ ] Cloud Function이 토큰의 회원과 조회 대상 회원이 같은지 검증한다.
- [ ] 위 검증 전에는 개인 API 통합과 개인 캐시의 일반 사용자 확대를 금지한다.

따라서 8단계의 성능 후보는 배포 가능하지만, 8단계 전체 보안 완료 체크는 서버 인증 연동 전까지 열어 둔다.

## 7. 배포 파일과 순서

1. Cloud Function의 `index.js`를 먼저 배포한다.
2. 실제 회원 응답의 `Cache-Control`과 `Pragma`를 확인한다.
3. 후보 `golfjoin_main.html`을 배포한다.
4. PC·모바일 비로그인 메인, 로그인 나의 모임·내예약, A/B 참여자 시나리오를 확인한다.
5. 문제가 있으면 HTML은 Phase 8 직전 백업으로 복원한다. 서버 헤더 변경은 기능 데이터 형식을 바꾸지 않으므로 HTML과 독립적으로 유지할 수 있다.

## 10. 1차 운영본에서 발견한 회귀와 교정

`30FE0097...`은 중복 요청 제거 자체는 정상 작동했다. 그러나 회원 보조 로더가 `home_bootstrap_light.newScheduleSummaries`를 공개 원본 목록 대신 재사용한 뒤, 이 “요약 행”을 Google Sheet의 “전체 신청 행”과 같은 정규화 함수에 다시 넣었다. 요약에는 `creatorPreview.gender`가 있지만 전체행의 `applicantGender` 필드는 없으므로, 생성자의 성별·프로필 일부가 빈 값으로 다시 만들어질 수 있었다.

교정 후보는 다음 경계를 강제한다.

- [x] 공개 요약은 `upsertLightNewScheduleSummary`로만 적용한다.
- [x] 회원 조회에서 받은 전체행만 전체 builder 정규화 함수로 적용한다.
- [x] 회원별 builder 캐시에는 공개 요약을 섞지 않는다.
- [x] 공개 요약 재적용 뒤 참여자 요약과 현재 회원의 참여 신청을 다시 병합한다.
- [x] 과거 1차 캐시에 요약 행이 남아 있어도 로컬 복원 시 요약 경로로 판별한다.

이 방식은 공개 `new_schedule_applications` 중복 GET을 다시 만들지 않으면서 A 생성/B 참여의 아이콘·배지·현재 인원·성별 구성을 보존한다.
