# 카카오 회원가입 완료 지연 v58 수정 계획

## 1. 결론

카카오 회원가입 마지막 화면의 `입력 완료` 이후 지연은 로딩 UI 자체가 아니라 여러 외부 요청을 순서대로 기다리는 구조에서 발생한다.

v56b는 과거 신청서 전화번호 동기화와 후보 안내를 완료 응답에서 분리했다. 그러나 현재 완료 경로에는 브라우저 ERP 확인, 중복 검사, ERP 저장, 브라우저 ERP 재확인, 서버 카카오 검증, 서버 ERP 재확인, Google Sheets 프로필 저장, 인증 세션 저장이 직렬로 남아 있다.

이번 v58의 1차 목표는 보안·정합성 순서를 바꾸지 않고 중복 왕복을 제거하는 것이다. 프로필 핵심 저장 전에 세션을 발급하거나, 서버의 카카오·ERP 신원 검증을 생략하는 변경은 하지 않는다.

## 2. 현재 완료 경로

```text
입력 완료
  → 브라우저 ERP 기존회원 확인
  → 아이디 중복 확인
  → 휴대폰 중복 확인
  → 이메일 중복 확인
  → ERP 외부회원 저장
  → 브라우저 ERP 재확인
  → Cloud Function 완료 요청
      → 카카오 token/info 확인
      → 카카오 user/me 확인
      → 서버 ERP 회원 확인 및 재시도
      → Google Sheets 프로필 헤더 확인
      → 프로필 전체 행 조회
      → 프로필 행 추가 또는 수정
      → GCS 인증 세션 저장
  → 로그인 완료 화면 이동
```

신규 회원 정상 경로에서도 브라우저와 서버를 합쳐 다수의 네트워크 왕복이 직렬로 이어진다. 서버 ERP 확인은 `[0, 500, 1000, 2000, 3500]ms` 재시도 정책을 사용하므로 ERP 반영이 늦으면 네트워크 시간과 별도로 최대 7초의 고정 대기가 추가된다.

| 우선순위 | 원인 | 코드 근거 | 영향 |

## 4. 유지해야 할 안전 조건

- [x] 카카오 액세스 토큰은 서버에서 공식 API로 검증한다.
- [x] 카카오 ID, ERP 회원번호, 이름, 휴대폰이 정확히 일치한 경우만 세션을 발급한다.
- [x] ERP 회원 저장 실패와 응답 유실을 구분하고 기존 멱등 복구 흐름을 유지한다.
- [x] 핵심 프로필이 내구적으로 저장되기 전에는 인증 세션을 발급하지 않는다.
- [x] 관리자 임시 명단 귀속과 탈퇴 후 재가입 복구를 유지한다.
- [x] 버튼 중복 클릭으로 ERP 회원·프로필·세션이 중복 생성되지 않게 한다.
- [x] 로그에는 이름·전화번호·카카오 토큰 등 개인정보를 남기지 않는다.

## 5. 최종 수정안

### v58a — 저위험 직렬 왕복 제거

- [x] 카카오 로그인 직후 ERP 미가입으로 판정된 사용자만 가입 폼에 진입하는 기존 Gate를 사용하고, 입력 완료 시 동일 ERP 사전 확인을 반복하지 않는다.
- [x] 아이디·휴대폰·이메일 중복 검사를 `Promise.allSettled`로 동시에 실행하고, 표시 우선순위는 기존과 동일하게 아이디→휴대폰→이메일로 유지한다.
- [x] ERP 저장 성공 후 브라우저의 두 번째 ERP 재확인을 제거한다. 서버 완료 API가 ERP 회원번호를 최종 확정하는 기존 테스트 계약을 사용한다.
- [x] ERP 저장 응답 유실·이미 생성된 회원·탈퇴 후 재가입은 현재 서버 최종 확정 경로로 복구한다.
- [x] 카카오 `token/info`와 `user/me`를 서버에서 병렬 요청한 뒤 두 응답의 사용자 ID와 앱 ID를 모두 검증한다.
- [x] 서버의 ERP 검증, 핵심 프로필 저장, 인증 세션 발급 순서는 그대로 유지한다.
- [x] `입력 완료`부터 화면 전환까지 단계별 소요시간과 ERP 재시도 횟수를 개인정보 없는 구조화 로그로 남긴다.
- [x] 로딩 문구를 `가입정보 확인 → 회원정보 생성 → 로그인 연결`로 단계별 표시한다.

예상 효과는 정상 신규가입 경로에서 브라우저 직렬 왕복을 최소 3~5회 제거하고, 카카오 검증 2회의 왕복을 1회 구간으로 겹치는 것이다. 실제 초 단위 목표는 자연 신규가입 로그를 확보하기 전에는 단정하지 않는다.

### v58b — 서버 병목이 남을 때만 적용

- [ ] ERP 직접 회원번호 조회 또는 더 좁은 검색 조건을 지원하는지 읽기 전용으로 검증한다.
- [ ] 직접 조회가 가능하면 이름 기준 광범위 조회를 회원번호·카카오 ID 기반 검증으로 교체한다.
- [ ] ERP 재시도는 성공률을 유지하는 범위에서 짧은 앞단 재시도와 명시적인 처리중 상태로 조정한다.
- [ ] Google Sheets 헤더를 리비전 단위로 캐시하고, 헤더 불일치 시에만 재확인한다.
- [ ] 프로필 행 조회·쓰기는 멱등성 및 관리자 임시 명단 병합을 유지하는 범위에서 요청 수를 줄인다.

프로필 저장을 단순 비동기 `fire-and-forget`으로 바꾸는 안은 Cloud Function 응답 후 작업 보장이 없고 세션만 발급된 유실 상태를 만들 수 있으므로 채택하지 않는다. 필요하면 먼저 GCS 내구성 outbox와 재처리자를 설계한 별도 단계로 진행한다.

## 6. 가입·탈퇴 반복 없이 수행할 검증

- [x] 지연을 주입한 가짜 ERP·카카오·Sheets·GCS로 전체 완료 경로를 시뮬레이션한다.
- [x] 정상 신규가입의 브라우저 ERP 확인 횟수와 중복검사 병렬 실행을 호출 순서 테스트로 고정한다.
- [x] ERP 저장 응답 유실 후 서버 복구, 기존회원 재개, 탈퇴 후 재가입을 각각 시뮬레이션한다.
- [x] 카카오 ID 불일치, ERP 회원번호 불일치, 휴대폰 불일치 시 세션이 발급되지 않는지 확인한다.
- [x] 프로필 저장 실패 시 세션 미발급, 재시도 시 동일 프로필 한 행 유지 여부를 확인한다.
- [x] 일반 카카오 로그인·일반회원 로그인·로그아웃·비로그인 메인·상품상세 회귀 테스트를 실행한다.
- [x] 운영 배포 후 기존 계정과 브라우저 콘솔을 회귀 확인한다.
- [ ] 다음 자연 신규가입 1건의 단계 로그만 관찰한다.

## 7. 단계별 배포와 중단 조건

1. v58a 서버·브라우저 후보와 복구본을 생성한다.
2. 모든 시뮬레이션과 기존 회원 인증 회귀가 통과해야 배포한다.

4. 메인 JavaScript·HTML을 반영하고 기존 계정 회귀를 다시 확인한다.
5. 다음 자연 신규가입에서 전체시간, 서버 ERP 재시도 횟수, 프로필 저장 상태를 확인한다.
6. 오류율 증가, 중복 프로필, 세션 미발급, 재가입 복구 실패 중 하나라도 발생하면 즉시 직전 v56b 서버·자산·HTML로 복구한다.
